# Design

## Context

См. [proposal.md](proposal.md) и [спецификацию поведения](specs/issue-comments/spec.md). Страница `src/app/(app)/[user]/[repository]/issues/[number]/page.tsx` использует серверную модель `getSingleIssue` и общий `Markdown`. Таблицы `comments`, `comment_revisions` и `issue_events` уже существуют. Импорт GitHub записывает диффы в `updated_content`, хранит снимки имени и аватара, а у части комментариев `author_id` пуст.

## Goals / Non-Goals

- **Goals** — встроить обсуждение в существующую страницу issue, обеспечить транзакционную историю и единые правила чтения, расширить действующий тестовый контур.
- **Non-Goals** — отдельное API обсуждений, новые роли уровня сайта, изменение модели приватных репозиториев, доставка уведомлений и управление реакциями в этой части лабораторной.

## Decisions

### Чтение и интерфейс

Страница issue и `CommentList` получают данные через серверные модели Drizzle. В `getSingleIssue` нужны внутренний ID и контекст видимости. `CommentItem` использует имеющиеся Avatar, Button и Markdown. Клиентскими остаются редактор, действия, просмотр истории и состояние ожидающих запросов. История загружается по запросу после повторной проверки доступа. Для публикации и правки используется существующий `MarkdownEditor` с сохранённым предпросмотром и управлением фокусом.

Курсор хранит ID issue и пару `(created_at, id)` без потери точности времени PostgreSQL. Запрос выбирает до 25 строк и одну дополнительную для определения следующей страницы. Значения курсора проверяются и связываются параметрами запроса. Индекс по `(issue_id, created_at, id)` для видимых строк поддерживает обход и подсчёт. Повреждённый курсор возвращает на первую страницу. Параметр `?comment=<id>` и якорь `#issuecomment-<id>` открывают окно списка около доступного комментария. Для скрытой или удалённой записи прямая ссылка возвращает заглушку. Курсор сохраняет порядок при одинаковых датах и при изменениях списка между запросами. Серверная выборка ограничивает размер первой загрузки.

### Доступ и модерация

Использовать `getAuthedUser` и `withAuth` для получения актора. Политика обсуждения проверяет канонический issue, `repositories.is_public`, принадлежность комментария к issue и право на действие. Контекст извлекается из БД. Гость читает публичное обсуждение, вошедший пользователь публикует, автор распоряжается своим комментарием, а владелец репозитория по `repositories.creator_id` скрывает и раскрывает. В этой части владелец исполняет роль модератора репозитория. Сравнение авторства выполняется по `author_id`. Снимки имени и аватара используются для отображения старых записей.

Обычный участник не публикует в заблокированном обсуждении. Самообслуживание автора для уже опубликованной записи остаётся доступным, а архивный репозиторий доступен только для чтения. Редактирование скрытого или удалённого текста запрещено до раскрытия или восстановления. Автор может восстановить свою запись из списка «Мои удалённые» после перезагрузки. Обычная заглушка скрытого комментария может показать причину. Состояние удаления имеет приоритет для общедоступного просмотра. Владелец читает скрытые версии из контекста модерации, а автор видит сведения о собственном удалении. Текст скрытых и удалённых версий исключается из обычных DTO, поиска, счётчиков, hovercard и признаков участия. Недоступная цель и подмена пары issue/comment дают одинаковый результат отсутствия ресурса.

### Состояние и транзакции

- Расширить `comments` полями `edited_at`, `deleted_at`, `deleted_by`, `version` и ключом запроса на создание. Для нового ключа сохранить отпечаток исходного текста, чтобы повтор после редактирования сравнивался с первоначальным запросом. Частичная уникальность по `(issue_id, author_id, client_request_id)` защищает от конкурирующих повторов и допускает старые строки без ключа.
- Сохранить `hidden` и `hidden_reason` как независимые от удаления поля. Мягкое удаление сохраняет связанные ревизии и реакции. Раскрытие удалённого комментария оставляет удаление, восстановление скрытого оставляет скрытие.
- Расширить `comment_revisions` признаком формата и идентификатором редактора. Старые записи остаются GitHub-диффами. Новая ревизия хранит прежний Markdown, редактора и время замены. Для импортированного комментария с историями дату последней правки брать из новейшей существующей ревизии до первой локальной правки.
- Переиспользовать `issue_events` для `ADD_COMMENT` и переходов удаления, восстановления, скрытия и раскрытия. Хранить ID комментария и акторские данные. Для записи о скрытии и раскрытии сохранить причину в событии, чтобы история пережила очистку текущего `hidden_reason`.

Новые действия в `src/actions/comment.action.tsx` принимают валидированные ID, Markdown, ключ создания или ожидаемую версию и допустимую причину скрытия. Пустой текст отклоняется. Предлагаемый предел текста — 65 536 символов, одинаковый для редактора, предпросмотра и записи. Модель в `src/models` повторно проверяет контекст под транзакционной блокировкой в порядке репозиторий, issue, комментарий. Для правок и переходов состояния используется проверка версии в записи. Действие записывает версию или событие только при фактическом изменении. Сбой ревизии или события откатывает основную запись.

```text
Server Action --> session + input validation
              --> BEGIN --> access + current state
                        --> comment + revision/event --> COMMIT
              --> route invalidation + confirmed result
```

### Безопасный Markdown и клиентские обновления

Сохранить публичные интерфейсы компонентов Markdown. Для недоверенного текста использовать разбор Markdown в дерево без выполнения MDX; перед рендерингом применять список разрешённых элементов, атрибутов и схем URL. Если для совместимости требуется сырой HTML, разобрать и очистить его перед преобразованием в React и дополнительно фильтровать атрибуты пользовательских React-компонентов. Сохранить проверенное отображение GFM и действующие GitHub-ссылки. Маркировку ссылок из доверенного разбора отличать от обычного HTML текста. Внутренние ссылки разрешать по владельцу, репозиторию и номеру с проверкой видимости. Тот же путь используется для preview, видимой версии и истории. Старые диффы выводятся как экранированный текст с оформлением диффа.

Оптимистичное создание использует один временный элемент с ключом запроса, правка — локальный черновик и сохранённое подтверждённое состояние. До подтверждения можно показывать экранированный текст или предыдущий безопасный предпросмотр. Успех заменяет временное представление DTO сервера; ошибка восстанавливает предыдущие данные и оставляет черновик. Повтор неизвестного результата создания использует тот же ключ. Конфликт версии загружает актуальное состояние и сохраняет введённый текст. Действия удаления и модерации обновляют представление по подтверждению сервера.

### Кэш и совместимость со списком issues

Добавить в `CacheKeys` ключ по репозиторию, ID комментария, версии содержимого и версии политики Markdown. KV хранит только безопасное дерево разметки или другой результат обработки, одинаковый для всех читателей. Проверка доступа выполняется до получения кэшированного содержимого. Результаты авторизации, тела скрытых версий и персональные данные обсуждения исключаются из общего кэша представления. После коммита обновить канонический маршрут issue и затронутый список issues. Новый ключ обновляет обработанный Markdown, поскольку инвалидация маршрута Next.js сама по себе не удаляет значения собственного KV. Сбой инвалидации фиксируется отдельно от результата уже завершённой записи.

Для списка issues заменить чтение счётчика комментариев из `comment_count_per_issue` на SQL-агрегацию видимых записей с тем же фильтром, что у обсуждения. Сохранить фильтр `in:comments`, обе сортировки по числу комментариев и значение ноль для пустого issue. После переноса потребителей убрать построчный триггер полного обновления счётчика комментариев. Счётчик реакций на issues использует свой существующий путь. Такой подход обеспечивает корректность после `UPDATE` видимости и исключает полный `REFRESH` в каждой транзакции создания.

## Risks / Trade-offs

- **Импорт может перезаписать обсуждение.** `scripts/fetchIssues.ts` удаляет комментарии и события перед загрузкой и содержит обновление без условия. Ограничить обновление ID вставленного комментария. Перед разрушительной заменой обсуждения проверять существующие комментарии и локальные события под той же блокировкой issue. Пропускать замену для уже заполненных обсуждений с явной диагностикой. Импорт нового issue остаётся возможным. Полноценная сверка удалённых и локальных записей потребует отдельной работы с идентификаторами GitHub.
- **Скрытые данные могут попасть в прежние запросы.** Применить фильтр видимости к поиску по содержимому, признаку авторства комментария и найденным упоминаниям из комментариев. Прямые ссылки и доступ к истории проверить отдельно с прогретым кэшем.
- **Изменение формата Markdown может затронуть README и issue.** Проверить существующие сценарии ссылок, списков задач и кода на исходных фикстурах. Сравнить поддержку безопасной разметки, которую использует уже сохранённый контент.
- **Известные проблемы baseline.** В AGENTS.md зафиксированы `TS2344` после генерации типов маршрута и предупреждение React о ключах в Markdown. Сравнивать проверку с исходным состоянием и фиксировать результат до и после изменений.

## Migration Plan

1. Проверить цепочку миграций на пустом PostgreSQL 12 и отдельной базе с импортированными комментариями, диффами, событиями и реакциями. Сверить фактические зависимости представления счётчика.
2. Добавить поля и индексы, сохранив совместимые значения по умолчанию и nullable поля для legacy-строк. Пометить существующие ревизии как диффы. Проверить новые значения перечисления событий на PostgreSQL 12 до их первого использования.
3. Согласовать переход счётчика и его потребителей. Пока предыдущая версия приложения читает материализованное представление, сохранить доступность представления. Убирать прежний триггер после перевода потребителей.
4. При откате отключить новый путь записи и сохранить текст, ревизии и аудит. Откат приложения после появления скрытых или удалённых комментариев допустим только к версии, которая уже применяет фильтр видимости. Изменения схемы с накопленными данными сохраняются.
